# 销售求职背景调查 — 目标公司求职情报手册

为销售岗位求职者对目标公司做背景调查，产出一份深度调研手册。交付以 **HTML（简约耐看版式）为主、md 配对**，可选 docx。
定位：**资深 B2B 销售求职者对目标公司的基本了解**——调研深、每句话站得住，但不越界到内部信息。

## 触发词

「销售求职背景调查」「对 XX 公司做背景调查（求职用）」「生成 XX 公司求职手册」「研究 XX 公司准备面试」

## 工作流（五步）

### Step 1 — 研究（WebSearch，只用公开信源）

按维度检索目标公司，每个数据点记下来源与口径：

1. 主营业务与核心产品线（含最新 AI/明星产品，重点展开）
2. 最新年度营收及盈利状况（非上市公司用券商估算，必须标注）
3. 标杆客户案例（按行业分组：汽车/互联网/金融/手机/媒体…）
4. 业务方向与战略布局、近期重大新闻（时间线）
5. **核心产品的竞品**（按产品线拆，不是云平台对比——查每个产品的直接对手、对手的客户画像、双方优劣势）
6. 行业大盘数据（市场规模、增速、推导逻辑）

### Step 2 — 固定结构（八章，顺序不可乱）

```
速览（4-6 个关键数字表 + 一段定位）
一、公司简介（是什么/为什么存在/母公司逻辑/公司现状）
二、核心概念速通（新旧模式对比表 + 术语卡，术语卡第三列=「对销售意味着什么」）
三、重点 AI 产品讲解（产品家族表格：功能×场景×客户群体；明星产品专讲；生态关系）
四、应用场景（场景×是什么×典型客户）
五、核心产品竞品全景（按产品线分小节，每节一张四列表）
六、行业大盘情报（关键指标表 + 推导链条 + 结论）
七、学习资源（求职者下一步行动，收尾）
尾注：数据口径总说明
```

**排序逻辑**：业务分析层层递进（公司→概念→产品→场景→竞品→大盘），最后落到求职者行动（学习资源收尾）。竞品章必须放在场景之后、大盘之前。

### Step 3 — 产出草稿（HTML + md，非终稿）

- **HTML 草稿**：modern-minimal 版式（见下）
- **md 配对**：同一内容存为 `XX公司_产品与销售手册.md`，两者一字不差
- 需要 docx 时走 tencent-docx 流水线（html-to-docx 转换）；用户偏好 HTML 时不必主动给 docx
- ⚠️ 此步产物**只是草稿**，必须依次通过 Step 4（可靠性闸门）与 Step 5（格式质检）后才可交付，禁止直接 present。

### Step 4 — 输出审查闸门（可靠性，终稿前必过）

在 Step 3 草稿落盘后、向用户展示前，**必须**先过本闸门。它是独立的可靠性检查步骤，核心目标只有一条：**用户绝不会收到错误、幻觉或不可靠的内容**。Step 4 与 Step 5 都失败/未过时，不得 present。

#### 4.1 触发时机

- **触发点**：Step 3 的 HTML 与 md 草稿写完即触发；未过本闸门不得进入 Step 5，更不得 present。
- **每次重跑**：用户要求"改一处"后的整本复核、重大修改、二次生成，都必须重跑完整闸门——不是只查改动点。
- **降级自审**：降级输出（见 4.5）本身也须再过一次本闸门的最小集（重点 D3 不编造），确保降级声明自身可靠。

#### 4.2 校验规则（五类，附默认严重级）

- **A 结构 / 语法（自动化脚本 `scripts/review_gate.py` 跑）**
  - A1 HTML 可解析、标签配平、单一标题（P0）
  - A2 md 与 HTML 章节标题集一致、内容一字不差（P0）
  - A3 八章齐全且顺序正确：速览 → 一 → … → 七 → 尾注（P1）
  - A4 无残留占位符 / 乱码 / TODO / `{{}}`（P0）；括号引号配平（P1）
  - A5 竞品四列表每行 4 列、无空单元格（P1）
- **B 逻辑一致性（脚本 + LLM）**
  - B1 竞品不把自家生态宿主当对手（例：钉钉是千问办公的嵌入宿主，不是竞品）（P1）
  - B2 低价 / 高价叙事不错配产品线（例：「价格激进」属豆包语言模型，非 Seedance 视频）（P1）
  - B3 同一数字全文口径一致（速览 / 现状 / 大盘三处对得上）（P1）
  - B4 章节衔接顺、无重复段落（P2）
- **C 请求一致性（LLM）**
  - C1 输出公司 = 用户请求的公司（P0）
  - C2 覆盖用户明确要求的维度（例：用户要最新 AI 产品 → 必有第三章；要竞品 → 必有第五章）（P1）
  - C3 未夹带用户要求剔除的内容（例：用户不要销售动作章 → 不得出现）（P1）
- **D 事实 / 口径（LLM + 溯源）**
  - D1 每个数字有来源标注，无裸数（P1）
  - D2 被官方辟谣数据已换口径 / 加提示（例：火山谭待辟谣过 Seedance 收入传闻 → 改用 ARR 口径）（P0）
  - D3 无臆造：引用产品 / 客户 / 新闻须有检索依据；无法确认标「待确认 / 未找到」而非编造（P0）
  - D4 新产品 / 早期数据（如公测 < 3 个月）标时效提示（P2）
- **E 边界与歧义（LLM）**
  - E1 请求超出能力（要内部薪资谈判策略、要非公开数据等）→ 主动说明边界，不答（P0 refuse）
  - E2 含义模糊 / 歧义（如「XX 公司」有歧义、不知指哪家）→ 请求澄清，不猜测（P0 clarify）
  - E3 数据高度不确定且无法验证 → 标「待确认」而非给确定数（P1）

#### 4.3 错误分级与处理策略

- **P0 严重（拦截 / 澄清）**：事实错误、幻觉（D3）、主题错（C1）、越界（E1）、歧义未澄清（E2）、HTML 损坏（A1）、被辟谣数据未处理（D2）。
  - **处理：禁止直接输出。**
    - 属可澄清的歧义 / 边界（E1 / E2）→ 向用户说明并请求澄清，不擅自作答。
    - 属已生成错误 / 幻觉（D3 / C1 / D2 / A1）→ 拦截并明确告知「哪部分无法确认 / 有误」；能修则回到 Step 3 修正并重审；无法修正且无可靠来源 → 删除该内容并标「待确认」。
  - 同类 P0 一出现即阻断，不计轮次。
- **P1 中等（修后重审）**：逻辑错配（B1 / B2）、口径缺失（D1）、章节顺序（A3）、竞品归属、请求维度遗漏（C2 / C3）、数字不一致（B3）、括号问题（A4 括号）、四列表不全（A5）、不确定数据未标（E3）。
  - **处理**：自动回写 HTML + md 修正，重跑闸门直到 P1 清零；记录修正项。若同类 P1 连续 3 轮仍无法修正 → 升级为 P0 降级输出。
- **P2 轻微（修正即过）**：排版细节（B4 重复段）、缺时效提示（D4）、括号小瑕。
  - **处理**：直接修正后输出，审查记录中备注，不阻断。

#### 4.4 自动化脚本

- 位置：`scripts/review_gate.py`（仅用 Python 标准库，无外部依赖，agent 直接调用）。
- 用法：`python3 review_gate.py --html X.html --md X.md --company 阿里云 --request "做阿里云调查" --out review_report.json`
- 覆盖：A1 / A2 / A3 / A4 / A5 及 D1 裸数启发式（裸数结果作 warn 交 LLM 裁定）。
- 输出 JSON：每项检查 `{rule, severity, status(pass/warn/fail), detail}`；含 `has_blocking`（任一 fail）；退出码 `0` = 无阻断，`2` = 有 P0/P1 fail。
- LLM 部分（B / C / D / E）由 agent 按 4.2 清单逐项自我审查，并合并写入审查记录。

#### 4.5 降级输出方案（审查失败时）

- **触发**：P0 未消解 / P1 连续 3 轮失败 / 触及能力边界（E1）/ 歧义未澄清（E2）。
- **动作：不输出「看似完整但不可靠」的手册。** 改为输出一份**诚实降级声明**，含：
  1. 已确认可靠的部分（若有通过段落）；
  2. 被拦截 / 无法确认 / 有误的部分及原因（P0 逐条列明）；
  3. 需要用户提供的澄清或补充信源；
  4. 若越界 → 明确「本 skill 不做 X」，并给替代路径建议。
- 该降级声明自身须再过一次最小审查集（重点 D3 不编造）后才输出。
- 全程记 `final_outcome = failed_degraded` 到审查日志。

#### 4.6 审查记录与持续改进

- 每次生成：脚本 JSON + 人类可读摘要，存 `<skill>/logs/review_<company>_<YYYYMMDD-HHMM>.json` 与工作区 `output/<manual>/review_log.md`。
- 记录字段：`timestamp`、`company`、`request`、`checks_run`、每条 `{rule, severity, result, detail, action(fixed/refused/clarify/noted)}`、`summary_grade`、`final_outcome(pass/degraded)`、`degraded_sections`。
- 持续改进：每次 fail / degraded 回流为新校验规则或铁律更新（darwin 机制），让同类错误不再复发。

### Step 5 — 格式质检与交付

- 过 Step 4 后，跑现有 `html-review`（genre=general）做版式质检，**必须通过**。
- 双文件 present（HTML 主 + md 配对）；可选 docx。
- 交付前确认：HTML 与 md 内容一致、尾注口径完整、降级声明（若有）已附。

## 内容铁律（反复迭代确认的偏好）

### 去 AI 味（最高优先级）

- ❌ emoji 做章节标题
- ❌ 「可抛观点」「面试速记」「弹药」「必背数据」这类花哨栏目
- ❌ 堆形容词、排比句、「赋能」「超级个体」等词
- ✅ 平实叙述，像内部 brief：只讲事实和口径
- ✅ 产品/竞品一律表格化；营收只放核心数字

### 口径纪律（可信度是命根子）

每个数字标注来源类型，三类必须分清：
- **公司公开口径**（发布会、官方宣传：如「超九成车企」）→ 标「公司公开口径」
- **第三方统计**（IDC/Omdia/QuestMobile/榜单）→ 标机构+时间
- **媒体测算/券商估算**（非官方）→ 标「媒体测算」；**被公司官方辟谣过的数据换口径或加提示**（例：火山总裁谭待辟谣过 Seedance 收入传闻→改用 ARR 口径并注明「引用时带据媒体报道前缀」）

### 视角纪律（外部求职者，不越界）

- ❌ 内部考核机制、内部战略细节当事实写
- ✅ 此类信息必须加「据公开报道」「公司公开表述」限定
- ✅ 洞察用「差异化逻辑：…」的客观表述，❌「打法上别和 X 拼…」的在职销售指令口吻

### 竞品章规范（核心章节）

- 按产品线拆小节（视频生成/图像/语言模型/智能体/编程与办公/搜索…），每节一张四列表：
  `竞品 | 客户画像 | 我方（该公司）优势 | 短板/对方强项`
- 自家生态产品（如字节的即梦、TRAE Work）要列出但标注「非外部竞品，属生态协同」
- 已退出赛道的竞品（如 Sora 关停）也保留一行，信息完整
- 注意低价/高价叙事不要错配到错误产品线（例：「价格激进」是豆包语言模型的事，Seedance 视频生成走高端定价）

### 防复发铁律（本次阿里云审计根因，darwin 回流）

两条硬纪律，违反任一条即视为 P0/P1，必须回写修正：

1. **数据时效锚定最新官方源**：所有动态数字（最新季度/财年、营收、ARR、连续增长季度数、芯片/产品版本、组织架构）**必须以官方最新财报/公告/发布会为锚（带具体日期）**，绝不以训练摘要、记忆旧口径或历史会话口径为准。
   - 生成 / 每次重大修改前**必须 WebSearch 现查**最新财报与公告，而非沿用上次的 summary 数字（数字会漂移，例：阿里「AI 收入连续增长季度数」会从 11→12 随 8-20 财报更新）。
   - 涉及「截至 X 月」「最新」的口径，文内统一标注抓取时点（如「2026-08-20 财报口径」）。
2. **跨产品线叙事不错配**：所有「营收/份额/规模领先」类表述**必须严格绑定对应口径 + 对应产品线**，禁止把一个产品线的优势套到另一个产品线：
   - 「AI 云收入第一」≠「MaaS 份额第一」≠「C 端用户规模第一」——三者分属不同口径（Omdia / IDC / 公司公开口径），混用即错配。
   - 同一指标在速览 / 现状 / 大盘 / 竞品多处出现时，**口径与数字必须完全一致**（B3）。
   - 竞品表「我方优势」一列只写该产品线真实优势，不写集团层面无关优势。

## HTML 版式规范（modern-minimal）

参照 tencent-docx design-token 的 general/modern-minimal 主题：

- 无封面页、无色块、无目录页、无红色强调数字
- 首页顶部：居中标题 + 一行元信息（「B2B 销售参考 · 数据截至 X 年 X 月 · 营收与份额为第三方机构估算口径」）+ 细分隔线
- 章节标题：纯黑加粗 15pt + 细底线；小节 13pt
- 表格：细线、无底色（表头浅灰）、9pt
- 正文 11pt、行距 1.7、两端对齐；单段提示用细左边框（note-line）
- 页脚页码；尾注（data-note）放全文最后
- 格式质检统一放在 Step 5 执行（html-review，genre=general，必须通过）；Step 3 生成阶段不做质检，避免顺序颠倒
