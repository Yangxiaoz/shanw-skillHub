# Skill 生产专家 — 把可复用场景做成 skill

把用户描述的「可复用场景」制作成完整 skill（SKILL.md + 审查脚本 + 参考示例），交付到 `<repo>/<skill-name>/`。
核心纪律一句话：**十要素缺一不可进入细节设计；先提议、经确认、再动笔。**

## 设计思想（对齐 job-intel，详见 references/golden-example.md）

job-intel 的八项机制全部保留，作用对象从「情报手册」换成「skill 本身」：

| job-intel 机制 | skill-create 对应物 |
|---|---|
| 固定八章结构 | 标准 SKILL.md 模板（见 Step 4） |
| 五步工作流，草稿≠终稿 | 五步工作流，蓝图未确认 ≠ 可写文件 |
| 输出审查闸门 | Step 5 交付前自审闸门（审查产出的 skill） |
| 降级输出方案 | 不交付半成品 skill，输出「设计声明」 |
| darwin 回流 | 生产中的缺失项 / 反复修正回流进十要素清单与铁律 |

## 触发词

「帮我把这个场景做成 skill」「做一个 XX 的 skill」「把这个流程包成 skill」「我要一个可复用的 skill」「skill 生产」

**不触发时机**：

- 一次性任务、不打算复用的流程 → 直接做，不制作 skill，并说明原因
- 已有 skill 覆盖的场景 → 指出现有 skill，建议复用或迭代，不新开
- 飞书 API 封装类（lark-cli skill）→ 走 lark-skill-maker
- 纯记忆型偏好（「以后都这样」）→ 写入 CLAUDE.md 即可，不需要 skill

## 工作流（五步）

### Step 1 — 需求采集与场景理解

1. 让用户自由描述场景（什么时候会用到、期望产出什么、有什么硬约束）。
2. 复述理解（场景 + 期望产出 + 已知约束），请用户确认对齐。
3. 判断是否值得做成 skill：一次性任务 / 已有 skill 覆盖 → 明确告知并给替代路径，不进入制作。

### Step 2 — 完整性核查（核心步骤）

对照「完整 skill 十要素清单」逐项核查用户描述中已有的信息：

| # | 要素 | 判据 |
|---|---|---|
| 1 | 场景用途 | 解决什么复用问题；为什么值得做成 skill |
| 2 | 触发词与不触发条件 | 具体触发短语；与邻近 skill 的边界 |
| 3 | 目标用户与视角 | 给谁用、站在什么立场 |
| 4 | 工作流步骤 | 分几步、每步做什么、步骤间依赖 |
| 5 | 固定产出结构 | 产出骨架（章节 / 文件），顺序固定 |
| 6 | 审查闸门规则 | 校验什么、错误分级（P0/P1/P2）、降级输出方案、审查记录 |
| 7 | 内容铁律与风格偏好 | 去 AI 味等硬约束 |
| 8 | 边界与拒绝条件 | 超出能力时：拒绝 / 澄清 / 降级 |
| 9 | 参考示例 | 一份 worked example 供对齐 |
| 10 | 与既有 skill 的关系 | 取代谁、补充谁、冲突时谁优先 |

- 已完整的要素：原样记入蓝图。
- 缺失的要素：进入**提议-确认循环**。

**提议-确认循环（本 skill 的核心机制）**，对每个缺失要素：

1. **先自行思考**：基于场景常识与 job-intel 设计思想，为该要素拟定一个具体、可直接采用的方案——写成能直接落进 SKILL.md 的文字，而不是把问题抛回给用户。
   - ❌「你想要什么样的审查闸门？」
   - ✅「建议闸门校验三类：A 结构（脚本，校验产出骨架与占位符）、B 一致性（LLM，校验覆盖用户要求）、C 事实（LLM + 溯源，每个数字标来源）。P0 拦截事实错误与结构缺失，草案如下：…」
2. **再询问是否采纳**：用 AskUserQuestion 呈现方案，选项固定为：
   - 「采纳」→ 方案记入蓝图
   - 「不采纳，我来说明」→ 以用户说明为准，原样记录
   - 「不采纳，换个思路」→ 回到第 1 步重新提议（连续 2 次未采纳，直接请用户说明）
3. **记录**：每次确认结果记入蓝图草稿；用户补充的内容原样记录，不得加工。
4. 同一批缺失要素可合并为一次提问（AskUserQuestion 支持 1-4 问），但每问都必须附带具体提议。

禁止事项：

- ❌ 十要素未齐就进入 Step 4 细节设计
- ❌ 缺失要素时只提问不提议（把思考成本推给用户）
- ❌ 用户说「随便」时真随便——「随便」= 授权采用第 1 步的提议，并在蓝图中标注「用户授权默认方案」

### Step 3 — 设计蓝图核对

1. 呈现完整蓝图：十要素逐条 + 目录结构 + 交付物清单。
2. 请用户逐条确认或修改；全部确认后蓝图**锁定**。
3. 锁定后用户再要求改动 → 重新核对受影响的要素，不静默改。

### Step 4 — 细节设计

按标准模板产出 skill 目录：

```
<skill-name>/
├── SKILL.md          # 标准模板，见下
├── scripts/          # 审查脚本（闸门含自动化项时必建，仅标准库）
├── references/       # worked example
└── logs/             # 审查记录（首次生成时创建）
```

标准 SKILL.md 模板（节序固定）：

```markdown
---
name: <skill-name>
title: <一句话标题>
description: <用途 + 具体触发短语 + 与邻近 skill 的边界>
---

# <标题>

<定位段：给谁用、解决什么、不越界到哪>

## 触发词

<具体触发短语 + 不触发时机>

## 工作流（N 步）

### Step 1 — …
### Step 2 — …
…
### Step N-1 — 审查闸门 <— 必含：校验规则、P0/P1/P2 分级处理、降级输出方案
### Step N — 格式质检与交付（若有）

## 内容铁律

<迭代沉淀的硬约束：去 AI 味、口径纪律等>

## 参考文件

<worked example 路径 + 对齐说明>

## 与既有 skill 的关系

<取代谁、补充谁、冲突时谁优先>
```

要素落点：1/3 → description 与定位段；2 → 触发词节；4/5 → 工作流节；6 → 工作流中的审查闸门步骤；7 → 内容铁律节；8 → 闸门 E 类规则 + 定位段；9 → 参考文件节；10 → 关系节。目录名与 frontmatter name 保持一致（job_search 目录属历史命名，新 skill 不再沿用）。

### Step 5 — 交付前自审闸门

产物落盘后、交付前**必须**过本闸门；未过不得交付。

#### 5.1 触发时机

- Step 4 文件写完即触发；未过闸门不得交付。
- 用户要求「改一处」后的复核、重大修改，重跑完整闸门，不是只查改动点。
- 降级输出（见 5.5）本身也须过最小自审（重点：声明真实、不谎称已确认）。

#### 5.2 校验规则（五类，附默认严重级）

- **A 结构 / 语法（自动化脚本 `scripts/skill_audit.py`）**
  - A1 SKILL.md 存在；frontmatter 完整（name/title/description 非空）（P0）
  - A2 必备章节齐全且顺序正确：触发词 → 工作流 → 内容铁律 → 参考文件 → 与既有 skill 的关系（P1）
  - A3 审查闸门完整：工作流内含「审查闸门」步骤 + P0/P1 分级 + 降级方案（P0）
  - A4 无残留占位符 / TODO / `{{}}`（P0）；括号引号配平（P1）
  - A5 SKILL.md 引用的本地脚本 / 参考文件实际存在（P0）
  - A6 引用的 Python 脚本可编译（P0）
- **B 可执行性（LLM）**
  - B1 每条工作流指令具体可执行，无「适当 / 酌情 / 灵活处理」类不可校验语句（P1）
  - B2 闸门每条规则有明确判据；脚本覆盖与 SKILL.md 描述一致（P1）
- **C 一致性（LLM）**
  - C1 description 触发短语与正文「触发词」节一字不差（P0）
  - C2 工作流步骤与闸门触发时机对应（P1）
  - C3 同一规则只在一处定义，全文无矛盾（P1）
- **D 需求一致性（LLM）**
  - D1 产出 skill 的用途 = Step 3 锁定的蓝图（P0）
  - D2 用户确认的十要素无遗漏（P0）
  - D3 未夹带用户明确不要的内容（P1）
- **E 边界（LLM）**
  - E1 与既有 skill 的边界已声明、无冲突（P1）
  - E2 蓝图仍有歧义 / 矛盾未澄清 → 回 Step 3 澄清，不猜测（P0 clarify）

#### 5.3 错误分级与处理策略

- **P0 严重（拦截）**：结构缺失（A1/A3/A4 占位符/A5/A6）、用途错（D1）、要素遗漏（D2）、触发词不一致（C1）、歧义未澄清（E2）。
  - **处理：禁止交付。** 能修 → 回 Step 4 修正并重审；信息依赖用户 → 回 Step 2 / Step 3 向用户补齐。同类 P0 一出现即阻断。
- **P1 中等（修后重审）**：章节顺序（A2）、可执行性（B1/B2）、一致性（C2/C3）、夹带（D3）、边界（E1）。
  - **处理**：自动回写修正，重跑闸门直到 P1 清零；同类 P1 连续 3 轮无法修正 → 升级为 P0。
- **P2 轻微（修正即过）**：格式小瑕。直接修正后交付，审查记录中备注。

#### 5.4 自动化脚本

- 位置：`scripts/skill_audit.py`（仅 Python 标准库，agent 直接调用）。
- 用法：`python skill_audit.py --skill-dir <skill-name> --out review.json`（macOS/Linux 用 `python3`）。
- 覆盖：A1 / A2 / A3 / A4 / A5 / A6；B / C / D / E 由 agent 按 5.2 清单逐项自审，合并写入审查记录。
- 输出 JSON：`{rule, severity, status(pass/warn/fail), detail}`；`has_blocking`；退出码 `0` = 无阻断，`2` = 有 fail。

#### 5.5 降级输出方案（审查失败时）

- **触发**：P0 未消解 / P1 连续 3 轮失败 / 十要素最终无法补齐。
- **动作：不交付半成品 skill。** 输出一份诚实「设计声明」，含：
  1. 已确认的要素与已通过的部分；
  2. 被拦截 / 缺失的要素及原因（逐条列明）；
  3. 需要用户提供的澄清或补充信息；
  4. 若超出本 skill 能力 → 明确「本 skill 不做 X」，给替代路径。
- 该声明自身须过最小自审（重点：不谎称已确认）后输出。
- 记录 `final_outcome = failed_degraded` 到审查日志。

#### 5.6 审查记录与 darwin 回流

- 每次生产：脚本 JSON + 摘要存 `<skill-name>/logs/review_<YYYYMMDD-HHMM>.json`。
- 记录字段：`timestamp`、`skill_name`、`request`、`checks_run`、每条 `{rule, severity, result, detail, action}`、`final_outcome(pass/degraded)`。
- darwin 回流：本次生产中出现的缺失项、反复出现的用户修正 → 回流为十要素清单新条目或内容铁律新条目，注明来源会话，让同类缺口不复发。

## 内容铁律（skill 写作规范，对齐 job-intel）

1. **可执行铁律（最高优先级）**：产出的 skill 中每条规则必须可执行、可校验。禁止「适当处理」「酌情考虑」类语句——要么给判据，要么给决策表，要么给示例。
2. **闸门必带铁律**：默认每个 skill 必须带审查闸门。场景确实轻量时，提议「最小闸门」（三条自检：产出结构 / 关键事实 / 边界），请用户确认后采用，不得无声省略。
3. **触发词一致铁律**：description 中的触发短语与正文「触发词」节一字不差；触发词必须具体到可识别的短语，禁止只有「当用户需要时」这类泛化描述。
4. **黄金示例铁律**：每个 skill 必须带 worked example 或指向对齐样例；没有现成样例时，先按本 skill 思路试跑一遍生成样例，经用户确认后收入 references/。
5. **单源铁律**：同一规则只在一处定义，其他处引用；禁止两处矛盾（审查闸门 C3 的由来）。
6. **去 AI 味**：不用「赋能」「抓手」「闭环」等词；平实叙述，像内部规范文档。
